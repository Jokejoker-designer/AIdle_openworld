## Authority POC requirements

- Run two distinct logical clients against one local authoritative world
  instance and one test space. The server owns canonical revision, entity state,
  ownership decisions and commit receipts.
- Client A submits one valid, schema-constrained proposal through the existing
  preview/confirm/commit boundary. Client B receives the committed event or a
  server snapshot and converges to the exact canonical revision and entity hash.
- Clients never write canonical state directly. An unconfirmed proposal, direct
  entity write, forged actor/client id, forged owner, stale expected revision,
  invalid schema, out-of-order event and altered commit receipt must fail closed.
- A duplicate idempotency key with the same canonical request returns the same
  receipt without duplicating an entity. Reuse with changed content returns a
  conflict and does not mutate state.
- Reconnect/replay from the last acknowledged revision must converge without
  double application. Missing or reordered events trigger snapshot resync or a
  structured failure, never silent divergence.
- Both clients must finish with identical canonical entity hashes and revision.
  Rejected forged attempts must leave those values unchanged.
- Use deterministic local fixtures only. Do not claim transport security,
  production authentication, matchmaking, Shared District scale, economy or
  durable server deployment.
